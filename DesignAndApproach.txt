After coming up with my schedule, I re-read over the supplied take home project documentation. From this I gathered key functional requirements and drafted the architecture that I wanted. I composed it of 5 parts:
Events - Simulated events that mimic the data that is being trasmitted from the machines on the production line.
Ingestion API - Validates requests, identifies duplicates, and persists accepted messages
Ingestion queue - This sits between the API and the message processor. API first saves messages to the queue. Messages have a status of Pending, Processing, Processed, or Failed. A BackgroundService processes queued messages and updates their statuses.
 -If the application restarts before a message is processed, the pending message remains in SQLite.
 -If processing fails, the message can be retried.
 -If processing is attempted twice, the database uniqueness constraint prevents a duplicate event.
 -If a message repeatedly fails, it can be inspected rather than retried indefinitely.
Processed Downtime Events - Validated records, queryable history
Dashboard - displays Production status, Downtime reports, and Ingestion health

Next, I set up my API. According to my 5 subsystem design, I knew that I would need an API for the Production Line, and another for the Ingestion.

    - GET operations

- The Ingestion API serves the purpose of performing 
    - GET operations
        - To read the health of the ingestion queue (counts of each message status)
        - To read an individual message by id 
        - To read a list of messages by status
    - POST operations
        - To submit a new machine event request to the message queue
- The Logs API serves the purpose of performing
    - GET operations
        - To read logs for machine events, ingestion messages, and permanent failures

Next, I set up my services. The services are comprised of an background service that queues ingestion messages, as well as the Sqlite logic. The background service polls the SQLite store every second and process 1 pending message at a time. The 2 actions of adding the event to the DowntimeEvents table and updating the ingestion message status to Processed is atomic via a transaction. This ensures that both commit together or neither do, in the case of a system crash. Upon system restart, any ingestion messages that are in the Processing status are reset to Pending so they can be retried.

One challenge for me was to be able to properly understand what classes to create. Taking the functional requirements and translating them into the classes and data transfer objects that fulfill the requirements while not being overengineered.

The greatest challenge however was making an at-least-once delivery queue behave idempotently without lying about the guarantees. I had to be explicit that this is at-least-once delivery with idempotent effects, not true exactly-once processing, and prove that with tests for duplicate replay, conflicting reuse, and crash recovery of in-flight messages rather than just asserting it in docs. I achieved this by using a durable accept-before-ack for the EnqueueAsync function that inserts the message into IngestionMessages table before returning a response, using atomic claiming with transactions when the worker claims a message, and restart recovery; setting messages with a status of 'Processing' back to 'Pending' on startup. At least once delivery + idempotent processing gets the same observable outcome as exactly-once, more like effectively-once.

Decisions and Trade offs

Idempotency / conflict handling
---
Used SourceEventId + a hash of the normalized payload as the idempotency key.
I hash the normalized payload so idempotency comparison is a cheap, fixed-size, canonical check rather than a fragile raw JSON comparison. Normalization happens first so logically identical events always hash the same, and the hash just gives me an efficient way to tell replay from conflict.
Trade-offs: 
 - SHA-256 is heavier than this use case needs, but its built into .NET with no extra dependencies.
 - Relying on System.Text.JSON to serialize. If the DTO's property order or JSonSerializerOptions ever change, the previously computed hashes for stored messages would no longer match newly computed hashes for logically identical resubmissions.

Relied on a DB unique constraint and caught the constraint violation, instead of check-then-insert; this avoids a race between concurrent duplicate submissions.
Same ID + same payload = replay, return 200 and log it. Same ID + different payload = conflict, 409. Only exact-ID collisions are covered; no semantic deduplicating across different IDs. An example would be two different machines assigning two different SourceEventIds to what was physically the same downtime event. Or a near duplicate event where the lind id, reason, and time windows are the same but the Ids are different. I took this trade off because accounting for this would require comparing the content of the events across different IDs which is more in depth than the scope of this project and also risks false positives.

Queue processing
---
Single-threaded background worker, one pending message at a time, polling on an interval.
Chose this over concurrent workers because the "only one ongoing event per line" rule would otherwise need per-line locking which is not worth the complexity here.
On crash, anything stuck in Processing resets to Pending on restart. Worker catches exceptions per loop so one bad message doesn't kill the whole service.
Trade-off: throughput is capped by sequential processing which is fine for this scope, wouldn't scale as-is.

Downtime calculation
---
Half-open interval math so events touching a report boundary don't get double-counted across adjacent windows.
Clip each event's duration to the overlap with the requested range; ongoing events get bounded by whichever is earlier, the report end or "now".
Reject inverted date ranges up front.

Why SQLite / raw SQL over EF Core
---
No separate DB server needed, easy to reset for a demo.
Wanted direct control over the unique-constraint-catch pattern and transaction boundaries for the idempotency logic. Raw SQL made that easier to reason about precisely.
Trade-off: more boilerplate, no compile-time query checking.

Known gaps, said plainly
---
Conflicts only go to console logs right now, nothing persisted/queryable. I'd add a table for it, same pattern as the existing duplicate-recognition audit log.
Classes mix entity and DTO concerns. I would split into *Entity/*DTO with real mapping.
Line status is stored separately from its downtime events and not synced, so they can drift apart.
Performance/Targets screens and OEE aren't built. OEE is the natural next metric given the data already captured.

Testing approach
---
Focused tests on the logic with real risk  (date-range math, idempotency/conflict/sequential processing) over simple CRUD, since that's where bugs actually hide.
